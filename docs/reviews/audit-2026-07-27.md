# Security & Correctness Audit — aria-mobile-core

**Date:** 2026-07-27
**Scope:** `src/lib.rs`, `src/gateway_client.rs`, `src/media.rs`, `src/dns.rs`, `src/types.rs`, `src/aria_mobile.udl`, `Cargo.toml` (~2266 LOC)
**Method:** Full read of all source under `src/`, plus verification of the `rtp-engine` `RtpHeader::parse` implementation (git checkout) for the RTP slicing path.
**Nature:** Adversarial audit only — no code was modified.

---

## Executive Summary

The crate is the shared mobile core (iOS/Android via UniFFI) handling SIP registration, gateway-routed call control, credential relay, and push-gateway heartbeat. Overall the code is reasonably careful in a few important places — **TLS verification is never disabled** (rustls, no `danger_accept_invalid_certs`), **no credentials are written to logs**, **no hardcoded secrets/default credentials exist**, and the SDP/RTP parsing paths are **bounds-safe** (I confirmed the RTP header slice cannot panic on malformed packets because `rtp-engine::RtpHeader::parse` validates CSRC and extension lengths before returning `Some`).

The material risks are:

1. **No transport security is enforced.** Nothing requires the gateway `base_url` to be `https://`. If it is `http://`, the plaintext **SIP password** and the **JWT bearer token** are sent over the wire in the clear. The SRV-resolution code path explicitly supports plain TCP / port 80.
2. **Panic-across-FFI fragility.** Every `Mutex`/`RwLock` acquisition uses `.unwrap()`. A single poisoned lock (e.g., a platform callback that unwinds while a lock is held) turns every subsequent engine call into a panic across the FFI boundary — a host-app crash / permanently bricked engine for a softphone.

The remainder are correctness/robustness issues (unbounded response allocation, `call_id` collisions, broken HTTPS failover, no-op push-token update, no token refresh) and low-severity hardening items (in-memory secret zeroization, log verbosity).

## HIGH

### 1. No transport-security enforcement — SIP password & bearer token can go over cleartext HTTP

**Severity:** HIGH
**Location:** `gateway_client.rs:92-104` (client construction), `:263-282` (register), `:442-462` (make_call); scheme handling at `:163-171`

```rust
// gateway_client.rs:92
pub fn new(base_url: String, api_key: String) -> Self {
    let http = reqwest::Client::builder()
        .timeout(Duration::from_secs(30))
        .build() ...
```
```rust
// gateway_client.rs:163  (resolve_gateway)
let is_tls = url.scheme() == "https";
let default_port = if is_tls { 443 } else { 80 };
...
let transport = if is_tls { dns::SipTransport::Tls } else { dns::SipTransport::Tcp };
```

The gateway `base_url` is taken verbatim from `GatewayConfig` (app-supplied) with no scheme validation. `register_device` (`:275`) and `make_call` (`:455`) serialize the **cleartext SIP `sip_password`** into the JSON body, and every request attaches the JWT via `.bearer_auth(token)`. `resolve_gateway` explicitly supports the non-TLS branch (`http` → port 80 → plain TCP).

**Failure/exploit scenario:** If the app is ever configured (or tricked, e.g. via a provisioning QR/URL) with an `http://` gateway URL, an attacker on the same network (open Wi‑Fi, malicious hotspot, on-path) captures the SIP account password and the gateway bearer token in plaintext — full account takeover and the ability to place/receive calls as the victim. There is no code-level guardrail preventing this.

**Recommended fix:** Reject non-`https` base URLs at `GatewayClient::new` (or in `AriaMobileEngine::new`), returning an error rather than constructing a client. If plain HTTP must be allowed for local development, gate it behind an explicit, off-by-default build feature and never in release. Also consider `reqwest::Client::builder().https_only(true)`.

### 2. Pervasive lock `.unwrap()` — a poisoned lock panics across the FFI boundary and crashes/bricks the host app

**Severity:** HIGH
**Location:** every `Mutex`/`RwLock` use, e.g. `lib.rs:119, 129, 136, 143, 296, 388, 448, 463, 483, 552, 558, 579, 587, 596, 605, 628, 629, 659`; also `gateway_client.rs:129,199,216`; `dns.rs:85,234,247`; `media.rs:103,164,252,333`

```rust
// lib.rs:129
if let Some(handler) = self.event_handler.read().unwrap().as_ref() {
    handler.on_call_state_changed(info.clone());
}
```

Every lock acquisition uses `.unwrap()`, which panics if the lock is **poisoned**. A lock becomes poisoned when a thread panics while holding it. Two realistic poisoning sources exist here:

- **Foreign callbacks invoked under a held lock.** `emit_call_state` (`:128`) calls the platform `MobileEventHandler` while holding the `event_handler` read lock. A Swift/Kotlin callback that raises/unwinds propagates a panic back through UniFFI; the read guard's Drop then marks the `RwLock` poisoned. From then on, `set_event_handler`, every `emit_call_state`, and `register_device` all `.unwrap()`-panic.
- **Any future panic inside a critical section** has the same cascading effect.

Because these methods are the UniFFI-exported surface, a panic here is a **panic across the FFI boundary** — with `panic = "abort"` (common for mobile `cdylib`/`staticlib` release profiles) it aborts the whole app; even with unwinding, the engine is permanently bricked (every call panics), so a softphone silently stops registering and receiving calls.

**Recommended fix:** (a) Never call foreign callbacks while holding a lock — clone/`take` the handler `Arc` out, drop the guard, then invoke. (b) Replace `.lock().unwrap()`/`.write().unwrap()` with poison-tolerant access (`match … { Ok(g)=>g, Err(p)=>p.into_inner() }`, or a `parking_lot` mutex which does not poison), so a stray panic cannot brick the engine. (c) Ensure exported functions never `unwrap` on state that outlives a single call.

## MEDIUM

### 3. Unbounded response body — `resp.json()` has no size limit (OOM)

**Severity:** MEDIUM
**Location:** `gateway_client.rs:245, 302, 384, 482, 512` (and every other `.json()`/`.await` body read)

```rust
let body: TokenResponse = resp.json().await?;
```

`reqwest::Response::json()` buffers the entire response body into memory with no cap. A compromised gateway — or an on-path attacker when TLS is absent (see Finding 1) — can return a multi-gigabyte body and OOM-kill the app. SDP strings (`sdp_offer`, `sdp_answer`, `caller_uri`, `caller_name`) are then handed to parsers with no length bound.

**Recommended fix:** Enforce a maximum body size before decoding — read with `Content-Length`/streamed `bytes()` capped to a few hundred KB, or wrap responses so bodies over a sane limit are rejected. Reject implausibly large SDP/URI fields too.

### 4. Incoming `call_id` collision — only 8 chars of `call_token` are used as the map key

**Severity:** MEDIUM
**Location:** `lib.rs:281`

```rust
let call_id = format!("incoming-{}", &call_token[..8.min(call_token.len())]);
```

The active-call map is keyed on `call_id`, but for inbound calls that key derives from only the first 8 characters of `call_token`. Two concurrent (or back-to-back) incoming calls whose tokens share an 8-char prefix produce the same `call_id`; the `calls.insert` at `:297` overwrites the earlier entry. The overwritten `ActiveCallState` is dropped without stopping its media session or poll thread → orphaned RTP/poll threads and mid-call controls (`hangup`, `set_mute`) act on the wrong call. (Outgoing calls use a full UUID at `:347` and are unaffected.)

**Recommended fix:** Use a collision-free `call_id` (full `call_token` hash or a fresh UUID) for inbound calls, matching the outgoing path.

### 5. SRV self-resolution defeats TLS hostname validation for HTTPS failover targets

**Severity:** MEDIUM
**Location:** `gateway_client.rs:178-190`

```rust
let host_port = if (is_tls && t.port == 443) || (!is_tls && t.port == 80) {
    t.addr.ip().to_string()
} else {
    format!("{}:{}", t.addr.ip(), t.port)
};
format!("{}://{}{}", scheme, host_port, path_prefix)
```

For failover, the client resolves the domain itself and then builds `https://<IP>...`. When reqwest/rustls connects to a URL whose host is an IP literal, it validates the certificate against that **IP**, not the original domain. Public certs carry domain SANs, not IP SANs, so every HTTPS failover request fails certificate validation. This "fails closed" (not a confidentiality hole) but means the SRV failover feature is silently non-functional over TLS — the resilience the module advertises does not work.

**Recommended fix:** Preserve the original hostname for TLS (SNI + cert verification) while directing the connection to the resolved IP — e.g. keep `https://<domain>:<port>` in the URL and use reqwest's `.resolve(domain, socketaddr)` / a custom DNS override to pin the target IP. Do not put the raw IP in the URL for `https`.

### 6. `update_push_token` is a silent no-op

**Severity:** MEDIUM
**Location:** `lib.rs:218-227`

```rust
pub fn update_push_token(&self, _device_id: String, _new_token: String) -> Result<(), MobileError> {
    log::info!("Push token update — re-registration required");
    Ok(())
}
```

The function returns `Ok(())` and does nothing. APNs/FCM tokens rotate; when they do and the platform calls this API expecting the change to propagate, the gateway keeps the stale push token and **the device stops receiving incoming-call pushes** — a silent, hard-to-diagnose loss of inbound calling. Returning `Ok` actively hides the failure.

**Recommended fix:** Implement re-registration with the new token (or add a gateway `PATCH /v1/devices/{id}` call). If it genuinely cannot act yet, return an error so callers can fall back to unregister+register, rather than a success that masks the gap.

### 7. No auth-token expiry or refresh handling

**Severity:** MEDIUM
**Location:** `lib.rs:141-147` (`get_token`), token stored once at `:174-177`

```rust
fn get_token(&self) -> Result<String, MobileError> {
    self.auth_token.read().unwrap().clone().ok_or(MobileError::AuthenticationError)
}
```

`TokenResponse.expires_in` is deserialized and then discarded (`#[allow(dead_code)]`, `gateway_client.rs:32-33`). The token is cached at registration and reused indefinitely. Once it expires, every subsequent operation (`make_call`, `accept_incoming_call`, heartbeat, status poll) fails with an auth error and there is no re-authentication path — the app is stuck until a full manual re-register.

**Recommended fix:** Track `expires_in`, and on a 401 / near-expiry transparently re-mint the token via `create_token` (when `api_key` is not a supplied JWT) and retry once.

### 8. `runtime()` panics across FFI if called before `init_runtime()`

**Severity:** MEDIUM
**Location:** `lib.rs:53-55`

```rust
fn runtime() -> &'static tokio::runtime::Runtime {
    RUNTIME.get().expect("Runtime not initialized — call init_runtime() first")
}
```

Every network-facing exported method calls `runtime()`. If the host app invokes any of them before `init_runtime()` (ordering bug, or a background push handler racing app startup), this `.expect()` panics across the FFI boundary and crashes the app.

**Recommended fix:** Lazily initialize the runtime via `get_or_init` inside `runtime()`, or have exported methods return `MobileError` when the runtime is absent rather than panicking.

## LOW

### 9. Secrets kept in plaintext memory, never zeroized

**Severity:** LOW
**Location:** `types.rs:14` (`SipCredentials.password: String`), `lib.rs:78` (`auth_token: RwLock<Option<String>>`), `gateway_client.rs:16` (`api_key`)

SIP passwords, the gateway API key, and the JWT live in plain `String`s for the process lifetime and are never wiped on drop, leaving them recoverable in memory/core dumps. Inherent to a relay design, but hardening is cheap.

**Recommended fix:** Wrap secrets in `zeroize::Zeroizing`/`secrecy::Secret` so buffers are cleared on drop, and avoid gratuitous `.clone()` of secret strings.

### 10. `notify_network_change` heartbeat bypasses SRV and the configured client

**Severity:** LOW
**Location:** `lib.rs:624-657`

The network-change heartbeat builds `format!("{}/v1/devices/{}/heartbeat", base_url, did)` from the raw `base_url` and issues it with a throwaway `reqwest::Client::new()` — bypassing the SRV failover list, the 30s timeout, and (if `base_url` is `http`) transport security (Finding 1). It also duplicates the existing `GatewayClient::device_heartbeat` (`gateway_client.rs:321`).

**Recommended fix:** Route the heartbeat through the shared `GatewayClient::device_heartbeat` so it inherits SRV/timeout/TLS behavior.

### 11. Fragile JWT detection heuristic

**Severity:** LOW
**Location:** `gateway_client.rs:107-109`

```rust
pub fn api_key_is_jwt(&self) -> bool { self.api_key.starts_with("eyJ") }
```

Treating any credential beginning with `eyJ` as a ready-to-use bearer token (skipping `/v1/auth/token`) is a brittle content sniff; a non-JWT secret that happens to start with those chars would be sent as a bearer token, and a real base64url JWT header need not start exactly with `eyJ`.

**Recommended fix:** Make the credential type explicit in `GatewayConfig` (e.g. an enum `ApiKey | Jwt`) rather than inferring it from a prefix.

### 12. `android_logger` pinned to `Debug` in all builds

**Severity:** LOW
**Location:** `lib.rs:31-35`

Debug-level logging is compiled into every build. While no secrets are currently logged, the SDP/URI/`device_id`/`src`-address traces are verbose and would surface any future accidental secret logging into logcat.

**Recommended fix:** Use `Info`/`Warn` in release (gate the level on `cfg!(debug_assertions)` or a feature).

### 13. Hardcoded `8.8.8.8:80` connectivity probe

**Severity:** LOW
**Location:** `media.rs:596`

```rust
if sock.connect("8.8.8.8:80").await.is_ok() {
```

Local-IP discovery falls back to a hardcoded connect to Google DNS. This is a fixed third-party dependency and a minor privacy signal (every fallback reveals the client to 8.8.8.8), and it fails in networks that block it.

**Recommended fix:** Use the gateway/registrar host for the routing-table probe, or make the probe target configurable.

## Positive Observations (verified, not issues)

- **TLS verification is never disabled.** `reqwest` is built with `rustls-tls` and default cert verification; no `danger_accept_invalid_certs`, `danger_accept_invalid_hostnames`, or custom no-op verifier anywhere. (The real gap is *enforcing* TLS — Finding 1 — not broken verification.)
- **No credentials are logged.** Passwords, API keys, and tokens are never passed to `log::*`; only non-secret identifiers (device_id, URIs, URLs without secrets) appear.
- **No hardcoded secrets or default credentials.**
- **RTP/SDP parsing is bounds-safe.** `media.rs:191` `&buf[header.header_length()..len]` cannot panic: I verified `rtp-engine::RtpHeader::parse` returns `None` unless the buffer is long enough for the CSRC list and any extension, so `header_length() <= len` always holds. SDP slicing (`media.rs:480` `line[9..]`) is guarded by the preceding `starts_with` prefix, and port/PT parses use `.parse().ok()`.
- **Push payload does not enable SSRF.** `handle_push_notification` ignores `PushCallPayload.gateway_url` and uses the trusted configured gateway; a malicious push cannot redirect the client to an attacker host.
